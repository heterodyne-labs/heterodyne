# 0010 Agent loop: local worktree pickup, one PR per ticket, fresh review responder on GitHub-hosted runners

## Context and problem statement

On 2026-10-14 the owner fixed the loop: an agent picks up a ticket, creates a branch and worktree, implements completely, and opens a PR; two persona bots review it (ADR 0011); the feedback is addressed; the owner merges. Implementation agents run locally on megatron on the owner's Max plan. The workstation has no public address, so GitHub cannot reach it, and the repository is public. Who addresses review feedback, with what context, and what starts it?

The owner decided on 2026-10-15 that the responder is a fresh agent: "I also don't think the original implementer agent should pass a handover doc to the feedback implementer agent as to not bias it in any way. Key design decisions will get recorded into an ADR-store anyway [...] I don't think there should be any form of communication, both direct or indirect, between the original implementer agent and the feedback implementer agent." The owner also agreed that the responder may read the PR description and commit messages, chose option A for the trigger, and put megatron's nightly suspend out of scope.

## Decision drivers

- The responder starts unbiased by the implementer's reasoning.
- No untrusted code may run on the workstation.
- Free tiers only; implementers and responders use the Max plan.
- Review rounds must not loop forever or overlap.

## Considered options

1. Responder on GitHub-hosted runners via `anthropics/claude-code-action` with the Max OAuth token (option A).
2. Local polling with conditional requests, responder in the local worktree.
3. A push relay (an Actions step to ntfy.sh, a local subscriber).
4. A self-hosted runner on the workstation.
5. Webhooks to the workstation (smee.io, `gh webhook forward`, tunnels) or Claude Code Routines.
6. Keep the implementer alive, or resume its session, to answer reviews.

## Decision outcome

Chosen option: 1, because it has the fewest moving parts, runs while the workstation is off, is documented by Anthropic for CI use with a subscription token, and runs no fork code on the owner's machine.

- Pickup: local, one git worktree and branch per ticket, on the Max plan. Only tickets the owner has reviewed are actionable. Open decision: whether pickup also moves to GitHub-hosted runners. Open decision: the orchestration driver (a pickup script run by hand, or a poller), the concurrency limit, and branch and worktree naming.
- One PR per ticket, trunk-based on `main`, squash merge only. The owner is the only merger.
- Conventional Commits, kept terse and lowercase, for commits and for the PR title that becomes the squash commit.
- Responder: a fresh agent for each review round, on a GitHub-hosted runner via `anthropics/claude-code-action@v1`, authenticated with `CLAUDE_CODE_OAUTH_TOKEN` generated by `claude setup-token`. No handoff document and no direct or indirect channel from the implementer. It may read the PR body, commit messages, ADRs, the diff, the reviews and CI results, and anything committed on the branch, such as the OpenSpec change folder.
- The reviewer bot posts with a GitHub App token or a PAT, because events caused by the workflow's `GITHUB_TOKEN` start no new workflow runs (only `workflow_dispatch` and `repository_dispatch` are exempt).
- `allowed_bots` names only the reviewer bot's login, never `*`. The workflow's `if:` also checks the review author and that the PR's head repository is this repository, so fork PRs never run it; they get no secrets anyway.
- A round cap stops fix-and-review loops. Open decision: its value and mechanism (the 2026-10-14 research proposed two or three automated rounds, counted with a label).
- A concurrency group per PR, such as `responder-<PR number>`, keeps rounds on one PR from overlapping.
- Fallback if option A fails: local polling of each open PR's reviews with conditional requests (`If-None-Match` with the stored ETag); a 304 does not count against the primary rate limit. Open decision: the polling interval (the research used 60 s).
- Out of scope: megatron's nightly suspend; the loop is not designed around it.

### Consequences

- Good, because responses run while the workstation is off, at no Actions cost on a public repository's standard runners.
- Good, because no fork code ever runs where the Claude login, SSH keys and `gh` token live.
- Good, because the responder judges the code on its merits, with reasons supplied by the ADRs.
- Bad, because the runner has no user-level config (global CLAUDE.md, user skills, local MCP servers); only repository config loads, from the base branch.
- Bad, because the OAuth token expires after one year and sits in the public repository's Actions secrets.
- Bad, because responder runs count against the same Max five-hour and weekly limits as the implementers.
- Bad, because the UK Consumer Terms served to megatron say "Non-commercial use only"; this was flagged on 2026-10-15 and the owner chose to proceed.
- Bad, because tacit reasoning that is not in an ADR, the PR body or a commit message is lost to the responder by design.

### Confirmation

- The responder workflow sets `allowed_bots` to one login, a per-PR concurrency group and the round-cap guard; a bot review on a test PR exercises it end to end.
- main's ruleset allows squash merges only.
- The responder prompt lists exactly the permitted inputs above.

## Pros and cons of the options

### GitHub-hosted responder (option A)

- Good, because Anthropic documents the token "For CI pipelines, scripts, or other environments where interactive browser login isn't available".
- Bad, because of the `GITHUB_TOKEN` trap and the 6-hour job limit.

### Local polling

- Good, because the responder could run in the local worktree, and nothing posted overnight is lost.
- Bad, because the machine must be on, and polling shares the user's 5,000 requests per hour.

### Push relay through ntfy.sh

- Good, because it reacts in seconds.
- Bad, because it adds a third party and a secret topic, and still needs a reconcile poll.

### Self-hosted runner

- Bad, because GitHub warns that "self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment."

### Webhooks or Routines

- Bad, because webhooks need a public endpoint or a relay that is dev-only by its own docs, and Routines cannot trigger on review or comment events.

### Keep or resume the implementer

- Good, because it keeps the implementer's reasoning.
- Bad, because the owner ruled out any implementer-to-responder channel, and one documented resume of a long implementer overflowed its context and dropped the review comments.
